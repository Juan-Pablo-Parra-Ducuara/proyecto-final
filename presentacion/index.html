Proyecto final · votación en el aula

Clicker
por cámara

Los alumnos levantan una tarjeta QR con la respuesta A/B/C/D. Una webcam local detecta el giro, envía el voto por Socket.IO y el profesor ve el resultado en vivo.

FastAPISocket.IO 5Microfrontends OpenCVPostgreSQLRedis
Requisito funcional

Qué resuelve

Una votación rápida, sin apps en el móvil y con resultados inmediatos.

👩‍🏫

Profesor

Controla la sesión desde el dashboard: elige pregunta, abre/cierra la votación y ve KPIs, participación y gráfica.

🎓

Alumno

Usa su tarjeta QR impresa. La gira 0°/90°/180°/270° para elegir A/B/C/D. No necesita instalar nada.

📷

Módulo local

Webcam en el PC del docente con OpenCV. Detecta hasta 2 QR por fotograma, valida estabilidad y envía el voto.

Resultado: conteo en vivo + cierre persistente en PostgreSQL con results:final.

Cumplimiento 1/12 · Secretos

“Nunca hardcodear secretos; usar variables de entorno validadas”

Cómo funciona

Settings(BaseSettings) declara los campos obligatorios y SettingsConfigDict(env_file=(".env", "../.env")) los lee del entorno. get_settings() está cacheado con lru_cache.

database_url: str
redis_url: str
api_key: str
secret_key: str
dashboard_password: str
port: int = 8000

Dónde está

  • backend/app/config.py — validación con pydantic-settings.
  • .env — valores locales reales, ignorado por Git.
  • .env.example — plantilla sin secretos.
  • .gitignore — ignora .env y .env.*.
  • local-module/client.py — load_project_env() lee el mismo archivo.
Evidencia: el commit no incluye .env. Los tests sobrescriben las variables en conftest.py con valores de prueba (test-password, test-secret-key).
Cumplimiento 2/12 · Event loop

“Nunca bloquear el event loop”

Cómo funciona

  • Los handlers de Socket.IO son async def.
  • SQLAlchemy usa create_async_engine con asyncpg.
  • Redis usa redis.asyncio.
  • Las operaciones se hacen con await: hgetall, sismember, pipeline.execute(), db.commit().

Código real

@sio.on("vote:cast")
async def vote_cast(sid, data):
    ok, reason, tally, student_id = (
        await services.cast_vote(...)
    )
    await sio.emit("tally:update", tally, room="dashboard")

backend/app/sockets.py y backend/app/services.py.

Evidencia: no hay time.sleep, psycopg2 ni cliente Redis síncrono en handlers. Los tests de sockets corren contra un uvicorn real con socketio.AsyncClient.

Cumplimiento 4/12 · Microfrontends

“Host, import(), mount(root), bus y sin imports cruzados”

Qué se pidió y qué hace

  • index.html + shell.js son el host.
  • Cada carpeta se carga con import() nativo desde registry.js.
  • Cada MFE exporta mount(root) y devuelve limpieza.
  • Cada uno es dueño de su view.html y su CSS.
  • Comunicación solo por bus.js; ninguno importa a otro.

Código real

const modulo = await definiciones[nombre]();
const limpieza = await modulo.mount(root);
activos.set(nombre, { limpieza, root });

// limpieza al desmontar
activo.limpieza?.();
activo.root.innerHTML = "";
Evidencia: dashboard monta scanner, live y results sin importarlos. live publica results:history y results solo lo escucha. node --check pasó en shell.js y auth.js.
Cumplimiento 5/12 · Persistencia

“INSERT ... ON CONFLICT (session_id, student_id) DO UPDATE”

Cómo funciona

cast_vote() persiste cada voto válido con upsert. close_session() vuelve a persistir el lote final con el mismo upsert, marca la sesión closed, hace commit() y solo después limpia Redis. Si ya estaba cerrada, devuelve los resultados existentes sin reescribir.

stmt = pg_insert(Vote).values(filas)
stmt = stmt.on_conflict_do_update(
    index_elements=["session_id", "student_id"],
    set_={"option": stmt.excluded.option},
)
await db.execute(stmt)
await db.commit()
# después del commit
await _cleanup_redis(session_id)
Evidencia: backend/app/services.py líneas 544-562 y 447-464. Tests de sesión y sockets verifican que el último voto gana y que el cierre es idempotente.

Cumplimiento 10/12 · Cookie firmada

“No incrustar API_KEY en el HTML; dashboard con cookie firmada”

Cómo funciona

URLSafeTimedSerializer(SECRET_KEY, salt="clicker-dashboard-session") firma la cookie clicker_session. Se envía con HttpOnly, SameSite=Lax y Secure si es HTTPS. El socket la lee desde HTTP_COOKIE.

Qué cambió respecto al plan inicial

  • El módulo local hace login en consola y conecta como dashboard.
  • El ticket de escritorio da acceso al navegador sin password doble.
  • auth={role:"local", api_key} se conserva solo como legacy del backend.
  • El estudiante tiene su propia cookie clicker_student_session.
Evidencia: login con 12345 → 200; contraseña antigua → 401; ticket reutilizado → 401; API_KEY no aparece en frontend/.

Cumplimiento 12/12 · Contrato y consistencia

“Contrato de eventos, salas y consistencia Redis/Postgres”

Eventos y salas

connect → state:sync, vote:open, vote:cast, vote:accepted, vote:rejected, tally:update, vote:close, results:final. Salas: local, dashboard, students, student:{id}.

Los payloads a estudiantes se saneen con student_open_payload() y student_results_payload().

Consistencia

  • Postgres gana si active_session apunta a una sesión cerrada.
  • cleanup_stale_active_session() se llama en el lifespan.
  • El cierre borra las claves Redis después del commit.
  • Cierre idempotente: si ya está closed, devuelve resultados sin reescribir.
Evidencia: main.py lifespan, services.py close_session() y cleanup_stale_active_session(), sockets.py rooms.

Salas y permisos

local

Módulo de cámara. Hoy entra con cookie de dashboard; API key solo legacy.

dashboard

Profesor con cookie firmada. Puede abrir/cerrar y escanear QR.

students

Todos los alumnos. Solo apertura y cierre de votación.

Reglas de negocio

Validación de vote:cast (en este orden)

  1. Sesión vigente. Si session_id != active_session → stale_session.
  2. Sesión abierta. Si no hay sesión abierta → closed.
  3. Identidad. Resolver qr_token o aruco_id y comprobar que está en session:{id}:roster → unknown.
  4. Opción. Si no es A–D → invalid.
  5. Válido: HSET en session:{id}:votes, recalcular con HGETALL (≤50 alumnos), emitir tally:update y vote:accepted.
El alumno puede cambiar de tarjeta: el último voto sobrescribe el anterior. Al cerrar se aplica ON CONFLICT DO UPDATE.
Esquema PostgreSQL

Tablas y restricciones

TablaCampos clave
studentsid, name, aruco_id (único), email, password_hash, qr_token, created_at
questionsid, text, option_a…d, correct_option, created_at
voting_sessionsid, question_id → questions, status (open/closed), opened_at, closed_at
votesid, session_id, student_id, option, created_at · único (session_id, student_id)
Checks

votes.option, questions.correct_option ∈ A/B/C/D. status ∈ open/closed + índice.

Tiempos

Todo con TIMESTAMPTZ y created_at DEFAULT now().

Claves y consistencia

Redis: estado en vivo

active_session                     → id de la sesión abierta
session:{id}:votes                 → hash {qr_token: "A|B|C|D"}
session:{id}:roster                → set de tokens habilitados
session:{id}:counts                → hash derivado (opcional)
session:{id}:stability:{token}     → filtro de lecturas (opcional)
  1. Postgres es la verdad; Redis es caché.
  2. Al cerrar: mapear token → student_id, persistir en una transacción y borrar Redis después del commit.
  3. Cierre idempotente: si ya está closed, devolver resultados existentes sin reescribir.
  4. Al arrancar: si active_session apunta a una sesión cerrada en Postgres, borrar la clave.
Módulo local

El módulo local hoy

1. Login como la web

Pide la contraseña del dashboard en consola (12345 en local), hace POST /auth/login y guarda la cookie clicker_session.

2. Misma interfaz

Crea un ticket de un solo uso y abre http://127.0.0.1:8000/?desktop_ticket=.... El shell canjea el ticket y monta el dashboard ya logueado.

3. Detección

detector.py lee hasta 2 QR por frame, calcula el ángulo y exige estabilidad de 0,5 s antes de emitir.

4. Cliente

client.py mantiene voting_open, session_id y roster con threading.Lock, y escucha los eventos del servidor.

Se ejecuta con Python nativo de Windows: python main.py --show. El dashboard se abre solo; la cámara sigue detectando en segundo plano.
