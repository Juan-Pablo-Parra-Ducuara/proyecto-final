Proyecto final · votación en el aula

Clicker
por cámara

Los alumnos levantan una tarjeta QR con la respuesta A/B/C/D. Una webcam local detecta el giro, envía el voto por Socket.IO y el profesor ve el resultado en vivo.

FastAPISocket.IO 5Microfrontends OpenCVPostgreSQLRedis
Requisito funcional

Qué resuelve

Una votación rápida, sin apps en el móvil y con resultados inmediatos.

👩‍🏫

Profesor

Controla la sesión desde el dashboard: elige pregunta, abre/cierra la votación y ve KPIs, participación y gráfica.

🎓

Alumno

Usa su tarjeta QR impresa. La gira 0°/90°/180°/270° para elegir A/B/C/D. No necesita instalar nada.

📷

Módulo local

Webcam en el PC del docente con OpenCV. Detecta hasta 2 QR por fotograma, valida estabilidad y envía el voto.

Resultado: conteo en vivo + cierre persistente en PostgreSQL con results:final.

Cómo funcionan los microfrontends

Host: shell.js

  • Decide qué MFE montar según la cookie: auth, dashboard o student.
  • Limpia store, desmonta MFEs y corta el socket al cambiar de rol.
  • Canjea el ticket de escritorio para dejar el dashboard ya logueado.

Registro: registry.js

live: () => import(
  "../microfrontends/live/live.js"
)

Cada MFE exporta mount(root) y devuelve una función de limpieza.

MFE propio

“En vivo” es su propio microfrontend

Separado de resultados: uno muestra el presente, el otro el cierre.

live — En vivo

  • KPIs de A/B/C/D y total.
  • Barra de participación y chips de quién falta.
  • Gráfica Chart.js que se mueve con tally:update.
  • Escucha session:changed, students:changed, question:selected.
  • Publica results:history para alimentar a results.

results — Cierre

  • Resumen final con respuesta correcta.
  • Tabla por estudiante: opción y acierto.
  • Solo presenta: no importa live, escucha el bus.
dashboard monta scanner, live y results en tres slots propios.
Contrato Socket.IO · 1/2

Eventos y payloads

EventoDirecciónPayload
connectcliente → servidorCookie firmada (dashboard/estudiante/módulo) o auth: {role, api_key} legacy. Rechazo: ConnectionRefusedError.
state:syncservidor → clienteDashboard/local: {session_id, status, question?, options?, roster?, counts?}. Estudiante: sin roster ni conteos.
vote:openservidor → clientes{session_id, question, options, roster}. A students va saneado, sin correct_option.
vote:castlocal/escáner → servidor{session_id, qr_token, option}. También acepta aruco_id por compatibilidad.

Eventos y payloads (continuación)

EventoDirecciónPayload
vote:acceptedservidor → student:{id} y emisor{session_id, student_id, option}
vote:rejectedservidor → emisor{qr_token o aruco_id, reason: unknown|closed|invalid|stale_session}

Salas Socket.IO

Salas y permisos

local

Módulo de cámara. Hoy entra con cookie de dashboard; API key solo legacy.

dashboard

Profesor con cookie firmada. Puede abrir/cerrar y escanear QR.

students

Todos los alumnos. Solo apertura y cierre de votación.

student:{id}

Sala privada para acuse y resultado individual.

Importante: el socket del estudiante es de solo lectura. No puede emitir vote:cast. El voto lo envía la cámara local o el escáner del dashboard.
Reglas de negocio

Validación de vote:cast (en este orden)

  1. Sesión vigente. Si session_id != active_session → stale_session.
  2. Sesión abierta. Si no hay sesión abierta → closed.
  3. Identidad. Resolver qr_token o aruco_id y comprobar que está en session:{id}:roster → unknown.
  4. Opción. Si no es A–D → invalid.
  5. Válido: HSET en session:{id}:votes, recalcular con HGETALL (≤50 alumnos), emitir tally:update y vote:accepted.
El alumno puede cambiar de tarjeta: el último voto sobrescribe el anterior. Al cerrar se aplica ON CONFLICT DO UPDATE.

Claves y consistencia

Redis: estado en vivo

active_session                     → id de la sesión abierta
session:{id}:votes                 → hash {qr_token: "A|B|C|D"}
session:{id}:roster                → set de tokens habilitados
session:{id}:counts                → hash derivado (opcional)
session:{id}:stability:{token}     → filtro de lecturas (opcional)
  1. Postgres es la verdad; Redis es caché.
  2. Al cerrar: mapear token → student_id, persistir en una transacción y borrar Redis después del commit.
  3. Cierre idempotente: si ya está closed, devolver resultados existentes sin reescribir.
  4. Al arrancar: si active_session apunta a una sesión cerrada en Postgres, borrar la clave.
Módulo local

El módulo local hoy

1. Login como la web

Pide la contraseña del dashboard en consola (12345 en local), hace POST /auth/login y guarda la cookie clicker_session.

2. Misma interfaz

Crea un ticket de un solo uso y abre http://127.0.0.1:8000/?desktop_ticket=.... El shell canjea el ticket y monta el dashboard ya logueado.

3. Detección

detector.py lee hasta 2 QR por frame, calcula el ángulo y exige estabilidad de 0,5 s antes de emitir.

4. Cliente

client.py mantiene voting_open, session_id y roster con threading.Lock, y escucha los eventos del servidor.

Se ejecuta con Python nativo de Windows: python main.py --show. El dashboard se abre solo; la cámara sigue detectando en segundo plano.

Autenticación

Login, cookies y ticket de escritorio

Web y módulo local

  • POST /auth/login con DASHBOARD_PASSWORD.
  • Cookie firmada clicker_session con SECRET_KEY.
  • /auth/me comprueba el rol; /auth/logout la borra.
  • Nunca se incrusta en el HTML.

Apertura del dashboard

  • POST /auth/desktop-ticket → ticket de un solo uso.
  • POST /auth/desktop-login → canjea ticket por cookie.
  • Caduca en 2 minutos y la URL se limpia.
  • API key queda solo como compatibilidad legacy del backend.
compare_digest codifica a bytes para soportar contraseñas con caracteres no ASCII.
